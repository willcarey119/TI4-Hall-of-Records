# Design Spec: V1.2 Analytics Expansion

**Date:** 2026-05-04
**Status:** Approved — ready for implementation planning

---

## Overview

Four new features extending the meta-dashboard analytics. Features 2, 3, and 4 are fully additive. Feature 1 extends the `VpSource` type with three new variants and changes how `vpSources` is computed in `buildGameStats` — the parser-level `VpEvent.source` value `'score_objective'` is kept as-is; only the aggregator output changes.

---

## Feature 1 — VP Source Breakdown: Split Objective Types

### Problem
The VP Source Breakdown currently shows a single `OBJ` bar aggregating all scored objectives. Stage I, Stage II, and Secret objectives have different strategic weights (1pt vs 2-3pt vs 1pt) and different difficulty — lumping them obscures where VP actually comes from.

### Solution
Replace the single `OBJ` row with three separate bars:
- **Obj · Stage I** — all `score_objective` events where `getObjectivePoints(name).stage === 'I'`
- **Obj · Stage II** — stage `'II'`
- **Obj · Secret** — stage `'secret'`

A thin dashed separator sits between the three Obj rows and the remaining sources (CUST, IMP, SFT, etc.). Each bar still shows total VP and share percentage.

### Data layer

`objectives.ts` already has the full lookup table with `stage: 'I' | 'II' | 'secret' | ...`. No parser changes needed.

**`buildGameStats.ts`** — change `vpSources` aggregation:
- Instead of bucketing all `score_objective` events together, run each event's `objective` name through `getObjectivePoints()` and bucket by stage.
- Emit three display keys in `VpSourceStat`: `'score_objective_stage1'`, `'score_objective_stage2'`, `'score_objective_secret'`.
- `VpEvent.source` in the parser continues to emit `'score_objective'` unchanged — the translation to three variants happens only inside `buildGameStats`, not at parse time. This avoids touching `gameReducer.ts`.
- Add the three new values to `VpSource` in `types.ts` alongside the existing `'score_objective'` (do not remove it — it remains valid for `VpEvent.source`).

**`VpSource` type addition** (in `types.ts`, append three new values):
```typescript
  | 'score_objective_stage1'
  | 'score_objective_stage2'
  | 'score_objective_secret'
```
`'score_objective'` stays in the union — used by the parser. The aggregator never emits it in `vpSources` output after this change.

**`SOURCE_LABEL` map** in `StatsSection.tsx`:
```
score_objective_stage1 → 'Obj · Stage I'
score_objective_stage2 → 'Obj · Stage II'
score_objective_secret → 'Obj · Secret'
```

### UI
In `StatsSection.tsx`, render the three Obj rows first with a dashed `<hr>` separator, then the remaining sources. No other UI changes.

### Testing
- Unit test: `buildGameStats` correctly buckets events by stage using the objectives lookup.
- Test unknown objective names fall through to a safe default (bucket as `score_objective_stage1` or skip, not crash).

## Feature 2 — Imperial + Mecatol Cross-Stat

### Problem
Imperial strategy card is the primary source of `imperial_point` VP — but only if the player controls Mecatol Rex when they play the primary. The aggregator tracks neither how often Imperial is played dry, nor what happened to Mecatol between card pick and primary play.

### Solution
A new sub-section within the Stats section (after the existing Mecatol Rex block) titled **"Imperial Strategy Card · Mecatol Correlation"**.

### Three states
Each Imperial primary activation is classified into exactly one state:

| State | Definition | Color |
|---|---|---|
| **Scored VP** | Faction owned Mecatol Rex at the time `END_TURN` with `selectedAction='Imperial'` fired | Red (accent) |
| **Contested away** | Faction owned Mecatol at strategy card pick time, but lost it before playing the primary | Orange (warm) |
| **No Mecatol** | Faction never held Mecatol that round | Muted (ink-3) |

**What can't be determined:** Whether "No Mecatol" cases were strategic blocks, failed capture attempts, or simple disinterest. The data has no tactical action target; this is documented in the UI footnote.

### Data layer

**New aggregator function: `buildImperialMecatolStats(games: ParsedGame[])`**

Returns:
```typescript
export interface ImperialMecatolStats {
  totalActivations: number;         // Imperial primary plays across all games
  scoredVp: number;                 // owned Mecatol at play time → got VP
  contestedAway: number;            // owned at pick, lost before play
  noMecatol: number;                // never held Mecatol that round
}
```

**Algorithm per game:**
1. Build a Mecatol ownership timeline from `planetEvents` filtered to `'Mecatol Rex'`, keyed by timestamp. A helper `mecatolOwnerAt(timestamp)` returns the faction ID that owned Mecatol at a given moment (or null).
2. Collect all `strategyCardEvents` with `card: 'Imperial'` and `type: 'pick'` → build a map `imperialPicks: Map<faction, pickTimestamp>`.
3. For each `strategyCardEvents` entry with `card: 'Imperial'` and `type: 'play_primary'`:
   - `ownerAtPlay = mecatolOwnerAt(event.timestamp)`
   - If `ownerAtPlay === event.faction` → state = `scoredVp`
   - Else `ownerAtPick = mecatolOwnerAt(imperialPicks.get(event.faction))`; if `ownerAtPick === event.faction` → state = `contestedAway`
   - Else → state = `noMecatol`

**Detection method:** Use `strategyCardEvents` with `type: 'play_primary'` as the authoritative source for Imperial activations — this event is emitted for all strategy card primaries regardless of whether VP was awarded. Do not use `vpEvents` for detection (it only covers the scored case).

### UI

In `StatsSection.tsx`, add after the Mecatol Rex block:

```
Imperial Strategy Card · Mecatol Correlation  [NEW badge]
[desc prose]

[4 stat boxes: Total | Scored VP | Contested Away | No Mecatol]
[bar: Scored VP ████████ 64%]
[bar: Contested away ███ 18%]
[bar: No Mecatol ███ 18%]

[footnote: "Contested away = owned at pick, lost before play.
No Mecatol = never held that round — could be strategic block,
missed capture, or disinterest. Cannot be distinguished from available data."]
```

Section only renders if `totalActivations > 0`.

## Feature 3 — VP Threshold Segmentation

### Problem
Aggregate stats like "Avg Winning VP: 11.4" are misleading when the dataset contains games played to different victory point thresholds (10, 11, 12, 14 pt). The average conflates fundamentally different game targets.

### Solution
A new **"Key Stats · By Victory Point Threshold"** table added to `StatsSection`, immediately after the headline 4-stat grid. The table shows All + one column per distinct threshold found in the actual game data, sorted ascending. Columns for thresholds not yet in the dataset are not shown (no placeholder columns for 14pt if no 14pt games exist).

### Data layer

**Step 1 — Expose `vpThreshold` on `ParsedGame`:**
- In `parseGame.ts`, `vpThreshold` is already derived (`rawOptions['victory-points'] ?? 10`).
- Add `vpThreshold: number` to the `ParsedGame` interface in `types.ts`.
- Store it in the returned object.

**Step 2 — Segment stats in `buildGameStats`:**
Add a new field to `GameStatsSummary`:
```typescript
export interface ThresholdSegment {
  vpThreshold: number;
  gameCount: number;
  avgWinningVp: number | null;
  avgDurationSeconds: number;
  avgPlayers: number;
  mecatol: MecatolStat;           // reuse existing type
}

// Added to GameStatsSummary:
byThreshold: ThresholdSegment[];  // sorted ascending by vpThreshold
```

Compute `byThreshold` by grouping the input games by `vpThreshold` and running the same sub-calculations as the top-level stats, but on each group independently.

### UI

In `StatsSection.tsx`, render the threshold table after the headline grid and before the Mecatol Rex sub-section:

- Header row: blank label cell | "All (N games)" | "10 pt (N games)" | "12 pt (N games)" | ...
- Most-played threshold column gets a subtle `background: var(--paper-2)` highlight and a ★ mark in its header.
- Stats shown: Avg Win VP, Avg Duration, Mecatol 1st Claimer Win%, Avg Players.
- Table uses `display: grid` with `grid-template-columns: 110px repeat(N, 1fr)` where N = 1 (All) + distinct threshold count.

### Scope constraint
Threshold segmentation applies **only to the Almanac table** in this feature. Faction win rates, tech stats, and strategy card stats are NOT segmented by threshold in this pass — that is future scope.

## Feature 4 — Strategy Card Section UI Redesign

### Two subsections redesigned

#### 4a — Most Picked by Round → Round Cards

Replace the current flat list (`R1 Politics ×3 | Imperial ×2`) with a card-per-round layout.

**Card design (per round):**
- Round number as large muted label (`R1` in Newsreader bold)
- Top 3 cards for that round, each showing: card name (Newsreader), pick count (×N), relative frequency bar (pick count / max pick count for that round)
- Top card bar uses `var(--accent)`, others use `var(--ink-2)` and `var(--ink-3)`
- Cards rendered in a `display: grid; grid-template-columns: repeat(auto-fill, minmax(100px, 1fr))` row — max 6 rounds across
- Rounds with fewer than 3 data points still render (just fewer chips)

**Data:** No change — `strategyCardStats.cards[].pickCountByRound[r]` already provides this.

#### 4b — Draft Position · Most Contested → 8-Card Grid

Replace the current `flexWrap` name list with a full 8-card grid (4×2), one card per strategy card, ranked by `avgPickPosition` ascending.

**Card design:**
- Rank label (`#1 most contested`, `#2`, ... `#8 least contested`) — IBM Plex Mono 9px, muted
- Card name — Newsreader bold body
- "Avg pick position" label — IBM Plex Mono 9px muted uppercase
- Position number — IBM Plex Mono display-sm, colored red for #1, muted for #8
- Relative frequency bar — pick count / max pick count across all cards
- Pick count label — IBM Plex Mono 9px muted

**Sorting:** Same as current — ascending `avgPickPosition`. Cards with no pick data sort last.

**Contested highlight:** Cards ranked #1–#2 get `border: 1px solid var(--ink-3)` (slightly more prominent). All others `var(--ink-4)`.

**Data:** No new data needed — `strategyCardStats.mostContested` and `strategyCardStats.cards[].avgPickPosition` already exist.

## Testing

- `buildGameStats`: VP sources now emit three OBJ variants — test all three stages; test unknown objective name graceful fallback.
- `buildGameStats`: `byThreshold` — test single-threshold dataset (only "All" and one threshold column); test multi-threshold; test `vpThreshold` not present on game (should fall through to 10).
- `buildImperialMecatolStats`: test all three states; test game with zero Imperial plays; test faction that picks Imperial but never plays primary.
- `parseGame`: `vpThreshold` present in returned object.
- UI components: no regression on existing tests.

---

## Out of Scope (this spec)

- Threshold segmentation for faction win rates, tech stats, or strategy card stats — future pass
- Imperial/Mecatol breakdown per-faction (which faction is most guilty of dry Imperial plays)
- Detecting *failed* Mecatol capture attempts from tactical action data (target system not available in current parser output)
